# 48：R01 补漏——损坏存档的有界读取与写前验证

实施：2026-10-15～16。本阶段完成上批自然 Walking 验收中发现的损坏存档解析崩溃修复及写前验证，不改战斗、美术、修炼、掉落或存档 schema；正式存档不用于故障试验。版本升级保护的剩余缺口单列下文，不把本批结果扩大为全部存档风险已解决。

## 原因与修复范围

旧读取函数只在长度小于 32 字节时提前返回，之后先调用引擎 `LoadGameFromMemory`，再检查类型和数据流末尾。错误 magic 会进入引擎的无头古老格式回退，把随机字节读成类名；即使头部正确，超长名称、类型树、数组数量及属性长度也可能先触发断言或分配。

本次改为项目侧纯字节检查与受信反射 schema 解码：

- 头部先检查 magic、GVAS 文件版本、UE 包版本、分支字符串、自定义版本格式／数量／GUID、精确 native SaveGame 类名和所有剩余字节边界；不尝试输入指定的类加载，不调用引擎的存档头读取或古老格式回退。
- 第一遍完整检查属性名、类型树、属性大小、可选 GUID、数组数量、嵌套结构、字符串编码与结束标记，不把输入名称驻留为 FName 或分配对象值；通过后才新建项目 SaveGame 对象，按同一规则第二遍解码。
- 支持当前持久图的数字、bool、FName、枚举、FGuid、项目结构体与 TArray。普通枚举按完整名称查找，Flags 枚举才作按位解析；FGuid 只按固定 16 字节读取。其他 native/custom struct serializer 和对象引用不自动放行，新持久类型必须显式补充支持。
- 已知字段严格匹配受信类型与 payload 长度；合法旧字段缺省保留构造默认值，已移除字段仅在验证 tag／类型树／Size 后按边界跳过，不交由引擎创建临时未知属性。增量保存可省略当前默认 `SaveVersion=23`，不能把该省略当损坏。
- 根对象控制扩展必须为无扩展；保留 root None 后的 4 字节 optional-GUID presence 边界及可选 16 字节 GUID 检查。该瞬态 UObject 身份注释不参与项目的值快照恢复；装备、法宝等属性中的持久 GUID 完整恢复。
- `LoadOrCreateSlot`、备份检查、显式恢复、保存前旧档检查共用新读取路径。原有缺失／不可读／较新 schema 分类与防覆盖、坏旧备份修复策略不变。
- 保存候选先在内存中用同一格式和预算验证，成功后才执行原有备份与主档写入，并只写已验证的同一份 bytes；非有限数字或超预算候选不得先改写备份。`CurrentSaveVersion` 仍为 23，输出仍是引擎原 SaveGame 格式。

## 支持边界与预算

| 内容 | 当前边界 |
| --- | --- |
| 整份已读取 bytes | 不超过 16 MiB |
| GVAS / CustomVersion | header 3 / Optimized 3；自定义版本最多 4096 个，GUID 非零且不重复 |
| UE 包格式 | UE4 字段等于本项目当前引擎，UE5 从完整 TypeName 格式起至当前包版本；本机 522 / 1012～1018 |
| header 字符串 | 最多 512 字符，精确结束符、无内嵌 NUL；UTF-16LE 检查 surrogate 配对 |
| 属性／值名称 | 不超过 `NAME_SIZE-1`，先检查编码范围再构造字符串／FName |
| 结构递归 / 类型树 | 深度小于 32；单树最多 64 节点，每节点最多 8 个子项，全局最多 262144 节点 |
| 属性 tag / 容器 | 最多 65536 个 tag；单数组及全局元素最多 65536，容器总预算 64 MiB |

项目 schema 1～23 与 UE 文件格式版本不是同一概念；支持当前 UE 格式承载的旧 schema 缺省与现有迁移，不能据此宣称任意历史 UE 发行档、重命名重定向或历史字段类型转换全部支持。更高 UE 文件格式、旧无头格式和不支持的已知字段类型保守拒读；不可读主档不自动重建或覆盖，不尝试自动格式转换。

两项原有版本保护缺口留作下一独立 R03 补验，不算本批已解决：

- 合法当前主档旁的不兼容 UE 文件格式备份，仍可能被原“坏旧备份修复”策略替换。当前仅能解读显式项目 schema 的版本，不能把未识别 envelope 的备份也宣称受同等较新版本保护。
- 未来构建若把 `CurrentSaveVersion` 改为 24，UE delta writer 也可能省略其默认版本值，旧构建则无法仅凭缺省判定来自未来。Schema24 测试是在当前 23 构建中写出显式 24，验证的只是显式标记保护；后续应保证生产快照始终含版本标记，并区分损坏与不兼容格式后再决定是否修复旧备份。

16 MiB 检查发生在平台 `LoadDataFromSlot` 已取得 bytes 后，不限制平台最初读取一个任意巨大磁盘文件的分配。结构正确的任意数值篡改也不等于可检测：本次未引入校验和、签名、加密或新文件格式。原有备份→主档顺序仍不是文件系统原子重命名；断电／磁盘故障及原生按钮交互不由本批证明。

- 新 `ImmortalPath.Save.MalformedPayload`：37 个独立负例，涵盖上述 ASCII、伪 magic、截断、字符串长度 INT_MIN／极大／超 FName 长度／未终止、错误类、自定义版本、类型树、属性长度／GUID、数组数量、实际 FName 值、缺结束符及后缀垃圾。每例覆盖坏主档、stale 拒写、字节保持、显式恢复、坏备份拒恢复及合法主档重建坏备份。
- 新 `CompatiblePayload`：9 个独立正例。反射填充全部持久字段及嵌套数组、非默认标量、FGuid、中文和 emoji FName；schema 1/6/15/20/22/23/24、受控旧字段省略和移除字段，与可信引擎 writer／loader 比较每个字段和重新序列化的完整 bytes。仅这些可信基准／合法 tag 变体交给引擎作参照，损坏负例绝不走该路径。这不是全部历史原档测试。
- 新 `GeneratedSnapshotProtection`：NaN 候选、65537 个 FName 的数组候选均应拒写，两个原档字节不变；数组候选另确认小于 16 MiB，确保覆盖数量预算而非文件大小上限；修回后能正常保存、重新读取与轮换备份。
- 包装器为每个例子启动独立进程／UserDir，使用完整测试名首尾锚点，严格检查实际报告仅 1 例成功、0 警告／失败／未运行／进行中、唯一完成标志、进程退出 0、无 Fatal、无残余 GUID 测试槽，并反复比对正式 22 个存档及 3 个新旧 BP 的集合与 SHA256。缺证据不能仅凭退出 0 判通过。
