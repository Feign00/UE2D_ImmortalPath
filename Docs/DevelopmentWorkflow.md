# 分阶段开发与 GitHub 交付流程

## 每个部分的完成条件

1. 明确本批范围与验收场景，检查分支、远程和未提交改动。
2. 实现最小完整部分，保持代码与素材依赖齐全；不顺手改动无关功能。
3. 编译、自动化测试、与改动相匹配的独立运行检查。测试由开发代理完成；环境确实无法验证的项目标记未验证，不将工作默认转交用户。
4. 复核差异，记录测试证据、已知限制与后续项。只读截图不能证明点击成功，帧数检查不能证明动作流畅。
5. 精确暂存本批文件，检查暂存区，再创建含明确范围的提交。
6. 普通推送到配置的 GitHub 远程，复核远程 SHA 与本地 SHA 一致；给用户简短阶段总结与提交链接。

依赖紧密、已经一起验证的历史积累允许作为一批基础提交，并在提交说明中列出子项；之后不再积累多个未经提交的阶段。没有必要为每个小文件创建独立提交，也不为拆分历史而制造不可编译的中间状态。

## 验证门槛

- 引擎：UE 5.7；运行时代码需要 `ImmortalPathEditor Win64 Development` 与 `ImmortalPath Win64 Development` 两个目标通过。
- 自动化：完整 `ImmortalPath.` 测试集；检查报告成功数、失败数、未运行数及测试日志，而非只看进程退出码。
- 独立运行：使用独立 `-UserDir`。透明桌面需用 DX11 原生合成验证；编辑器 PIE 和合成前洋红底截图不能代替桌面验证。
- UI：需要覆盖此次改动的页面切换、按钮、分辨率/缩放及返回路径。涉及退出则检查保存、退出时窗口状态与实际销毁。
- 动画：需要检查站立、移动循环、攻击接触点、密集受击、死亡/复活，以及脚线和比例稳定。生成图不等于完成运行素材。
- 正式主存档不得用于测试；需要记录的摘要可以入库，个人存档与完整运行日志保留本地忽略目录。
- 工具链内部异常如重试后消失，也要记录；不得通过关闭业务测试或修改引擎来掩盖项目错误。

## 仓库与发布边界

- 当前远程：`origin`，GitHub 项目 `Feign00/UE2D_ImmortalPath`。沿用现有分支，不擅自改变分支保护或合并策略。
- 每次 GitHub 推送是源码阶段同步，不等同于打包发行版。当前没有配置可运行 UE 的云端 CI，不声称 GitHub 自动编译已经通过。
- 不上传 `Binaries`、`Intermediate`、`Saved`、`DerivedDataCache`、`Releases` 或凭据。正式素材应附来源/生成记录，超过 GitHub 限制的文件先制定 LFS/发布方案，不强行上传。
- 不执行强推、远程删分支或历史清洗；远程出现新提交时先审查兼容性。
